### B. Faulty SQL clause diagnosis (`C02`)
To be **25 years old in completed years on `2026-09-25`**, a customer's 25th birthday must be on or before `2026-09-25` (`birth_date <= '2001-09-25'`) and their 26th birthday must be strictly after `2026-09-25` (`birth_date > '2000-09-25'`), so **`birth_date` $\in [\text{'2000-09-26'}, \text{'2001-09-25'}]$**.

Each of the three agreeing models writes a different faulty `WHERE` clause that selects **zero customers**, and `COALESCE(SUM(...), 0)` converts the empty `NULL` sum into the exact same default integer **`0`**:

```sql
-- 1. groq:openai/gpt-oss-20b (TD1/traces-td1.csv line 23) -> returns 0
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE c.birth_date > '2025-09-25' AND c.birth_date <= '2026-09-25';

-- 2. openrouter:cohere/north-mini-code:free (TD1/traces-td1.csv line 44) -> returns 0
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM customers c
JOIN orders o ON c.customer_id = o.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE c.birth_date <= '2026-09-25' AND
      date(c.birth_date, '+25 years') > '2026-09-25' AND
      date(c.birth_date, '+26 years') <= '2026-09-25';

-- 3. openrouter:dots-studio/dots-3-note-preview:free (TD1/traces-td1.csv line 88) -> returns 0
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE c.birth_date IS NOT NULL
  AND strftime('%Y-%m-%d', 
       CAST((strftime('%Y', '2026-09-25') - strftime('%Y', c.birth_date)) AS INTEGER) || '-' ||
       strftime('%m-%d', c.birth_date)) <= '2026-09-25'
  AND strftime('%Y-%m-%d', 
       CAST((strftime('%Y', '2026-09-25') - strftime('%Y', c.birth_date) + 1) AS INTEGER) || '-' ||
       strftime('%m-%d', c.birth_date)) > '2026-09-25';
```

- **Why `gpt-oss-20b` returns `0`:** `c.birth_date > '2025-09-25' AND c.birth_date <= '2026-09-25'` subtracts **1 year instead of 25 years**, testing customers aged **0** (born between 26 September 2025 and 25 September 2026). No customer in `boutique.sqlite` is born in 2025–2026.
- **Why `north-mini-code:free` returns `0`:** `date(c.birth_date, '+25 years') > '2026-09-25' AND date(c.birth_date, '+26 years') <= '2026-09-25'` **inverts both inequality operators**. Requiring the 25th birthday to be strictly after `2026-09-25` while the 26th birthday is on or before `2026-09-25` is a logical contradiction ($\emptyset$).
- **Why `dots-3-note-preview:free` returns `0`:** `CAST((strftime('%Y', '2026-09-25') - strftime('%Y', c.birth_date)) AS INTEGER)` computes the year difference (e.g., `25`), concatenates `'25-' || strftime('%m-%d', c.birth_date)` $\rightarrow$ `'25-09-25'`, and passes it to `strftime('%Y-%m-%d', '25-09-25')`. Because SQLite requires a 4-digit year `'YYYY-MM-DD'`, `strftime` returns `NULL`, making the `WHERE` predicate unknown (`NULL`) for every row ($\emptyset$).

### B. Faulty SQL clause diagnosis (`C10`)
A customer is aged 25 in completed years on order date `o.date` in two calendar cohorts:
1. **Cohort 1 (`year(o.date) - year(c.birth_date) = 25` AND `MM-DD(o.date) >= MM-DD(c.birth_date)`):** turned 25 earlier in the same calendar year (or on the order date).
2. **Cohort 2 (`year(o.date) - year(c.birth_date) = 26` AND `MM-DD(o.date) < MM-DD(c.birth_date)`):** turned 25 in the previous calendar year and has **not yet reached their 26th birthday**.

```sql
-- Query D, groq:qwen/qwen3.8-27b (TD1/traces-td1.csv line 72) -> returns 119410
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE (
    (strftime('%Y', o.date) - strftime('%Y', c.birth_date)) = 25
    AND (strftime('%m', o.date) || strftime('%d', o.date)) >= (strftime('%m', c.birth_date) || strftime('%d', c.birth_date))
)
OR (
    (strftime('%Y', o.date) - strftime('%Y', c.birth_date)) = 24
    AND (strftime('%m', o.date) || strftime('%d', o.date)) < (strftime('%m', c.birth_date) || strftime('%d', c.birth_date))
);

-- Query E, openrouter:dots-studio/dots-3-note-preview:free (TD1/traces-td1.csv line 96) -> returns 119410
SELECT COALESCE(SUM(o.quantity_product * p.price), 0) AS revenue_cents
FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE 
    (CAST(strftime('%Y', o.date) AS INTEGER) - CAST(strftime('%Y', c.birth_date) AS INTEGER)) = 25
    AND (
        (CAST(strftime('%m', o.date) AS INTEGER) > CAST(strftime('%m', c.birth_date) AS INTEGER))
        OR (
            CAST(strftime('%m', o.date) AS INTEGER) = CAST(strftime('%m', c.birth_date) AS INTEGER)
            AND CAST(strftime('%d', o.date) AS INTEGER) >= CAST(strftime('%d', c.birth_date) AS INTEGER)
        )
    );
```

- `dots-3-note-preview:free` writes **only Cohort 1** (`year_diff = 25` and birthday reached) and completely omits Cohort 2.
- `qwen3.8-27b` writes Cohort 1, and in its `OR` branch writes `(strftime('%Y', o.date) - strftime('%Y', c.birth_date)) = 24` instead of `= 26` (testing customers aged **23**, of whom none ordered in `boutique.sqlite`).
- Both queries therefore select the exact same Cohort 1 subset (`119410` cents) and miss the entire Cohort 2 subset (`439570` cents).

### C. Delta diagnostic SQL query on `data/boutique.sqlite` (`C10`)
Executed on `../data/boutique.sqlite` and exported to [delta-c10-td2.csv](delta-c10-td2.csv):

SELECT c.customer_id,
       c.birth_date,
       MIN(date(o.date)) AS first_order_date,
       MAX(date(o.date)) AS last_order_date,
       (CAST(strftime('%Y', o.date) AS INTEGER) - CAST(strftime('%Y', c.birth_date) AS INTEGER)) AS year_diff,
       COUNT(o.order_id) AS order_lines,
       SUM(o.quantity_product * p.price) AS customer_revenue_cents,
       CASE
           WHEN (CAST(strftime('%Y', o.date) AS INTEGER) - CAST(strftime('%Y', c.birth_date) AS INTEGER)) = 25
                AND strftime('%m-%d', o.date) >= strftime('%m-%d', c.birth_date)
           THEN 'COUNTED_BY_D_AND_E'
           ELSE 'MISSED_BY_D_AND_E'

FROM orders o
JOIN customers c ON o.customer_id = c.customer_id
JOIN product p ON o.product_id = p.product_id
WHERE date(c.birth_date, '+25 years') <= date(o.date)
  AND date(c.birth_date, '+26 years') > date(o.date)
GROUP BY c.customer_id, c.birth_date, year_diff
ORDER BY status_in_faulty_queries, c.customer_id;

## 5. Checking Policy: Binary-Bitmask Canary Test (`100, 200, 400, 800` cents) and Its Limits

In production, no reference value exists on `boutique.sqlite`, and calling a stronger model is not a check (Lecture 2, slides 8, 9 and 11). To detect shared SQL age-window errors deterministically by code **before** counting a model's vote, `pair_b_wrong_consensus.py` implements `build_canary_db(ref_date, ...)`, which runs each generated SQL query against an in-memory 4-customer **binary-bitmask canary table** calibrated for the question's reference date (`2026-09-25` for `C02` and `C10`, and `2026-12-01` for `DEMO-SQL-C11`):

- **Bit 0 (`100` cts) — `K1`:** turns 25 on the reference date (`2001-09-25` or `2001-12-01`, Cohort 1) $\rightarrow$ **must include**.
- **Bit 1 (`200` cts) — `K2`:** turns 26 the day after the reference date (`2000-09-26` or `2000-12-02`, Cohort 2) $\rightarrow$ **must include**.
- **Bit 2 (`400` cts) — `K3`:** turns 26 on the reference date (`2000-09-25` or `2000-12-01`, aged 26) $\rightarrow$ **must exclude**.
- **Bit 3 (`800` cts) — `K4`:** turns 25 the day after the reference date (`2001-09-26` or `2001-12-02`, aged 24) $\rightarrow$ **must exclude**.

Because the four amounts are powers of two (`100, 200, 400, 800`), **only a query that selects `K1 + K2` returns `300`**, and any other sum diagnoses which boundary failed on the executed queries:
- **`300` (`K1 + K2`) $\rightarrow$ PASS:** `C02` reference SQL, `C10` reference SQL, and `C11` reference SQL.
- **`0` ($\emptyset$) $\rightarrow$ REJECT (empty-set bug):** catches all three faulty queries on `C02` (`gpt-oss-20b`, `north-mini-code`, `dots-3-note`) and `DEMO-SQL-C11` query `M2` (`north-mini-code`).
- **`100` (`K1` only) $\rightarrow$ REJECT (single-day or missed Cohort 2):** catches both faulty queries on `C10` (`qwen3.8-27b` and `dots-3-note`) and `DEMO-SQL-C11` query `M1` (`gpt-oss-20b`, which only matches `birth_date = '2001-12-01'`).

**Limits of the canary.** The canary is a targeted candidate check, not a general SQL correctness guarantee. It only tests the age window around one specific reference date with four synthetic boundary customers. A query with a wrong join, a wrong amount formula, a wrong period filter or duplicated rows could still return `300` on the canary while being wrong on the shop database. Moreover, it was designed after observing the completed-age errors of this batch and requires one canary table calibrated per question type and per reference date (a question on `2026-09-24` such as `C08`, or on `2026-12-01` such as `C11`, requires its own boundary dates, which adds a maintenance cost to consider in TD 3). For a customer-facing figure or a payout, the validated reference query of the family remains the check that decides.
